# PHASE 102 — SDD DATA MODEL & GRAPH DATABASE THINKING

Bu mərhələdə `.sdd`-yə artıq sadəcə folder kimi yox, **bir əlaqəli knowledge graph / engineering model** kimi baxacağıq.

Əsas sual:

> `.sdd` daxilindəki bütün obyektləri necə modelləşdirək ki, AI həm əlaqələri anlaya bilsin, həm də runtime bunları deterministic şəkildə icra edə bilsin?

# 102.2. Entity ≠ File

Çox vacib.

Məsələn:

```text
.sdd/project/users/tasks/TASK-100.sdd
```

file-dır.

Amma:

```text
TASK-100
```

entity-dir.

File sadəcə entity-nin representation-ıdır.

# 102.18. Tree vs Graph

Folder structure:

```text
users/
  tasks/
    TASK-100
```

tree-dir.

Amma real relation:

```text
TASK-100
 ├── implements REQ-100
 ├── requires SKILL-10
 ├── uses API-20
 ├── modifies TABLE-30
 ├── produces ARTIFACT-40
 └── verified_by TEST-50
```

graph-dir.

Bir entity bir neçə fərqli entity ilə əlaqəlidir.

# 102.19. Buna görə folder yalnız storage modelidir

≠
Domain Model

> insan və filesystem üçün navigation.

> semantic relationships üçün model.

# 102.61. Relational vs Graph vs Hybrid

| Model    | Güclü tərəfi                    | Zəif tərəfi                   |
| -------- | ------------------------------- | ----------------------------- |
| Files    | Sadə, Git-friendly              | Complex relations çətindir    |
| SQL      | Transaction, audit, consistency | Deep traversal daha çətindir  |
| Graph DB | Relationship/query çox güclü    | Operational complexity        |
| Hybrid   | Hər ikisinin üstünlüyü          | Architecture daha mürəkkəbdir |

### Mənim default seçimim:

```text
.sdd files
      ↓
PostgreSQL
      ↓
Logical Graph Layer
      ↓
Graph Queries
```

Başlanğıc üçün.

Sonradan graph workload həqiqətən böyüyərsə ayrıca graph database əlavə edilə bilər.
