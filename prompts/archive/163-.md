# PHASE 104 — SDD TASK ENGINE & TASK DECOMPOSITION

Bu mərhələdə `.sdd` sisteminin **TASK ENGINE** hissəsini qururuq.

Əsas problem:

> User bir böyük requirement verir. Sistem bunu necə düzgün, ölçülə bilən, dependency-ləri müəyyən edilmiş və AI tərəfindən icra edilə bilən task-lara çevirir?

Məsələn:

```text
"User authentication sistemi qur"
```

bu **task deyil**.

Bu, böyük bir **Requirement / Feature**-dir.

---

# 104.1. Requirement → Task

Sadə model:

```text
Requirement
    ↓
Feature
    ↓
Task
    ↓
Subtask
    ↓
Skill
    ↓
Execution
```

Məsələn:

```text
REQ-AUTH-001
    ↓
FEATURE-AUTH
    ↓
TASK-AUTH-001
TASK-AUTH-002
TASK-AUTH-003
TASK-AUTH-004
```

---

# 104.2. Task nədir?

Task:

> **tək bir məqsədi olan, konkret scope daxilində icra edilə bilən engineering work unit-dir.**

Yəni:

```text
Task
=
Goal
+
Scope
+
Input
+
Dependencies
+
Acceptance Criteria
+
Output
```

---

# 104.3. Task ≠ Requirement

Requirement:

> User login edə bilməlidir.

Task:

> Implement `POST /auth/login`.

Başqa task:

> Add password validation.

Başqa task:

> Add login integration tests.

---

# 104.4. Task ≠ Skill

Task:

```text
Implement login API
```

Skill:

```text
IMPLEMENT-API
```

Task deyir:

> **nə iş görüləcək**

Skill deyir:

> **bu iş hansı process ilə görüləcək**

---

# 104.5. Task ≠ Execution

Task:

```text
TASK-100
```

Execution:

```text
EXEC-500
```

Task specification-dır.

Execution real run-dır.

Eyni task bir neçə dəfə execute edilə bilər:

```text
TASK-100
 ├── EXEC-500 FAILED
 ├── EXEC-501 FAILED
 └── EXEC-502 SUCCESS
```

---

# 104.6. Task Lifecycle

Əsas lifecycle:

```text
DRAFT
 ↓
READY
 ↓
IN_PROGRESS
 ↓
BLOCKED
 ↓
DONE
```

Alternativ:

```text
CANCELLED
```

və:

```text
FAILED
```

execution state ola bilər.

Task ilə execution failure-ni qarışdırmamaq vacibdir.

---

# 104.7. Task State ≠ Execution State

Task:

```text
IN_PROGRESS
```

ola bilər.

Son execution:

```text
FAILED
```

ola bilər.

Çünki retry mümkündür.

# 104.12. Amma həddindən artıq decomposition də pisdir

# 104.17. Task Decomposition Rules

SDD rule deyə bilər:

```text
TASK MUST:
- have one primary goal
- have defined scope
- have acceptance criteria
- declare dependencies
- declare required skills
```

---

# 104.18. Task Completion Criteria

Task:

```text
DONE
```

olmaq üçün sadəcə AI:

> "Done."

deməməlidir.

Acceptance criteria yoxlanmalıdır.

Məsələn:

```text
AC-001
valid login → 200

AC-002
invalid password → 401

AC-003
expired token → 401
```

---

# 104.19. Acceptance Criteria ≠ Test

Acceptance Criteria:

> sistem hansı behavior-i təmin etməlidir?

Test:

> bunu necə yoxlayacağıq?

Məsələn:

```text
AC:
invalid password returns 401
```

Test:

```text
POST /auth/login
password = wrong

EXPECT:
401
```

---

# 104.20. BDD ilə əlaqə

Acceptance criteria:

```text
Given valid user
When login request is sent
Then access token is returned
```

Task engine bunu test generation üçün istifadə edə bilər.

# Növbəti mərhələ — PHASE 105

İndi task və skill sistemlərini birləşdirib **Agent Orchestration**-a keçəcəyik:

```text
TASK
 ↓
AGENT SELECTION
 ↓
CAPABILITY MATCHING
 ↓
SKILL ASSIGNMENT
 ↓
CONTEXT ISOLATION
 ↓
TOOL PERMISSIONS
 ↓
EXECUTION
 ↓
HANDOFF
 ↓
REVIEW
```

Əsas sualımız olacaq:

> **Bir task-ı hansı AI agent icra etməlidir və sistem bunu necə avtomatik seçməlidir?**

Burada `Agent`, `Role`, `Capability`, `Skill`, `Permission`, `Model`, `Tool`, `Cost`, `Risk`, `Autonomy` və **multi-agent orchestration** anlayışlarını `.sdd` architecture-a bağlayacağıq.
