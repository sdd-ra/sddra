# PHASE 110 — MULTI-AGENT ORCHESTRATION

İndi `.sdd` sistemini **tək agentli sistemdən multi-agent sistemə** keçiririk.

Əsas sual:

> Bir böyük task-ı bir neçə ixtisaslaşmış agent arasında necə bölmək, koordinasiya etmək və nəticəni təhlükəsiz şəkildə birləşdirmək olar?

---

# 110.1. Niyə Multi-Agent?

Tutaq ki requirement belədir:

```text
REQ-100:
Implement payment system
```

Bir agentə hər şeyi vermək:

```text
Architect
+ Backend
+ QA
+ Security
+ DevOps
```

çox böyük responsibility yaradır.

Bunun əvəzinə:

```text
REQ-100
   ↓
ORCHESTRATOR
   │
   ├── ARCHITECT
   ├── BACKEND
   ├── QA
   ├── SECURITY
   └── DEVOPS
```

daha idarəolunan olur.

---

# 110.2. Multi-Agent nə deməkdir?

Multi-agent:

> Müxtəlif responsibility-lərə malik agentlərin bir workflow daxilində koordinasiyalı işləməsidir.

Burada vacib məqam:

**Multi-agent ≠ sadəcə 5 LLM çağırışı.**

Əslində lazımdır:

```text
Agent
+
Role
+
Scope
+
Context
+
Permission
+
Task
+
Communication
+
Ownership
```

---

# 110.3. Agent Role

Hər agentin konkret rolu olmalıdır.

Məsələn:

```text
ARCHITECT
CODER
QA
SECURITY
REVIEWER
DEVOPS
DOCUMENTATION
```

Pis:

```text
GENERAL_AGENT
```

Hər şeyi edən agentin davranışını idarə etmək daha çətindir.

---

# 110.4. Agent Responsibility

Agent yalnız role ilə müəyyən edilməməlidir.

Məsələn:

```text
CODER
```

üçün:

```text
responsibility:
  implement application code
```

amma:

```text
not_responsible_for:
  production deployment
  security approval
  architecture approval
```

---

# 110.5. Agent Scope

Agent hansı hissədə işləyə bilər?

```text
scope:
  project: payments
  modules:
    - refund
    - transaction
```

Beləliklə agent bütün repository-ni dəyişmək hüququna malik olmur.

---

# 110.6. Agent Permission

Scope başqa, permission başqadır.

Məsələn:

```text
CODER
```

bunları edə bilər:

```text
READ_FILE
WRITE_FILE
RUN_TEST
```

amma:

```text
DEPLOY_PRODUCTION
```

edə bilməz.

```text

```

```text

```

# 110.15. Private Context

# 110.16. Niyə Private Context?

Əgər bütün agentlər bütün context-i görürsə:

```text

noise ↑
cost ↑
confusion ↑
```

Ona görə:

> **Minimum Required Context**

prinsipi istifadə etmək yaxşıdır.

# 110.17. Orchestrator

# 110.18. Orchestrator Agent deyil

Çox vacib:

```text
Orchestrator
```

mütləq LLM agenti olmaq məcburiyyətində deyil.

Hətta əsas workflow orchestration mümkün qədər deterministic ola bilər.

```text

Orchestrator

```

# 110.19. Supervisor Pattern

Bir supervisor digər agentləri idarə edir:

```text
             SUPERVISOR
            /     |     \
           /      |      \
       CODER      QA    SECURITY
```

Supervisor:

```text
assign
review
retry
escalate
```

edir.

---

# 110.20. Worker Pattern

Supervisor + workers:

```text
SUPERVISOR
    │
 ┌──┼────┐
 ▼  ▼    ▼
W1  W2   W3
```

Worker yalnız verilmiş task-ı həll edir.

Bu ən sadə multi-agent modellərdən biridir.

---

# 110.21. Pipeline Pattern

Agentlər ardıcıl işləyir:

```text
ARCHITECT
   ↓
CODER
   ↓
QA
   ↓
SECURITY
   ↓
REVIEWER
```

Bu `.sdd` üçün çox uyğun pattern-dir.

---

# 110.22. Parallel Pattern

Bəzi agentlər paralel işləyə bilər:

```text
          TASK
           │
     ┌─────┼─────┐
     ▼     ▼     ▼
    QA  SECURITY  DOCS
     │     │       │
     └─────┼───────┘
           ▼
         REVIEW
```

Bu execution time-ı azalda bilər.

---

# 110.23. Dependency Graph

Parallel execution yalnız dependency yoxdursa mümkündür.

Məsələn:

```text
ARCHITECT
   ↓
CODER
   ↓
QA
```

burada QA coder-dan asılıdır.

Amma:

```text
CODER
SECURITY ANALYSIS
DOCUMENTATION
```

bəzi hallarda paralel gedə bilər.

---

# 110.24. DAG

Bunu DAG kimi modelləşdirmək olar:

```text
        A
      / | \
     B  C  D
      \ | /
        E
```

A tamamlanır.

Sonra:

```text
B
C
D
```

paralel işləyir.

Sonra:

```text
E
```

başlayır.

---

# 110.25. Task Graph və Agent Graph eyni deyil

Çox vacib fərq.

### Task Graph

```text
TASK-A → TASK-B
```

deyir:

> İşlər hansı dependency ilə bağlıdır?

### Agent Graph

```text
ARCHITECT → CODER
```

deyir:

> Hansı agent hansı agentlə əlaqəlidir?

Onları bir-birinə məcburi bağlamaq lazım deyil.

# 110.44. Consensus


```text

```

# 110.48. Retry ≠ Escalation

Retry:

> Eyni agent yenidən cəhd edir.

Escalation:

> Daha yüksək səviyyəli agent və ya human işə qoşulur.

Məsələn:

```text
Coder
 ↓ retry ×3
FAILED
 ↓
Senior Coder
```

---

# 110.49. Multi-Agent Failure

Məsələn:

```text
CODER → FAILED
```

Bütün sistem dayanmalı deyil.

Orchestrator dependency graph-a baxır.

Əgər:

```text
QA
```

coder nəticəsindən asılıdırsa:

```text
QA → BLOCKED
```

olur.

Amma:

```text
DOCUMENTATION
```

asılı deyilsə:

```text
DOCUMENTATION → continue
```

edə bilər.

# 110.50. Partial Progress




# 110.63. Bu mərhələdə nə qazandıq?

Artıq sistem:

* bir neçə agent işlədə bilir;
* agentləri role ilə ayıra bilir;
* task-ları delegate edə bilir;
* parallel execution edə bilir;
* context-i idarə edə bilir;
* agent permission-larını məhdudlaşdırır;
* agent conflict-lərini idarə edir;
* review və validation edir;
* failure zamanı escalation edir;
* bütün agent fəaliyyətini trace edir.

Amma hələ böyük bir problem qalır:

> **Agentlər səhv qərar verə bilər. Sistem onların yaratdığı nəticənin həqiqətən doğru olub-olmadığını necə müəyyən edəcək?**

# PHASE 111 — VERIFICATION, VALIDATION & QUALITY ENGINE

Növbəti mərhələdə **"AI dedi ki, hazırdır" ilə "sistem sübut etdi ki, hazırdır"** arasındakı fərqi quracağıq.

Burada:

```text
Verification
Validation
Acceptance Criteria
BDD
Test Generation
Test Execution
Static Analysis
Security Analysis
Architecture Validation
Contract Testing
Regression Testing
Quality Gates
Evidence
Proof of Completion
```

və ən vacibi:

> **Task yalnız agent "done" dediyi üçün deyil, sistem bunu müstəqil evidence ilə sübut etdiyi zaman COMPLETED olacaq.**
