# PHASE 105 — AGENT ORCHESTRATION & CAPABILITY ROUTING

İndi `.sdd` sistemində **Task → Agent → Skill → Tool** əlaqəsini qururuq.

Əsas problem:

> Task hazırdır. Bəs bu task-ı **hansı agent** icra etməlidir?

Sadəcə:

```text
Task → AI
```

demək kifayət deyil.

Daha düzgün model:

```text
Task
 ↓
Capability Requirements
 ↓
Agent Discovery
 ↓
Capability Matching
 ↓
Policy Check
 ↓
Agent Selection
 ↓
Skill Execution
```

---

# 105.1. Agent nədir?

Agent:

> müəyyən capability-lərə sahib olub task-ları icra edən autonomous execution unit-dir.

Məsələn:

```text
AGENT-CODER
AGENT-ARCHITECT
AGENT-QA
AGENT-SECURITY
AGENT-DEVOPS
```

---

# 105.2. Agent ≠ Skill

Çox vacib fərq:

```text
Agent = WHO
Skill = HOW
Task = WHAT
Tool = WITH WHAT
```

Məsələn:

```text
Task:
Implement payment API

Agent:
Backend-Coder

Skill:
API-Implementation

Tools:
read/write/test
```

---

# 105.3. Agent ≠ Model

Agent:

```text
BACKEND-CODER
```

bir LLM modelinə bağlı ola bilər:

```text
Model-A
```

amma model dəyişə bilər.

```text
BACKEND-CODER
     │
     ├── Model A
     └── Model B
```

Agent identity və capability modeldən ayrılmalıdır.

# 105.7. Skill və Capability fərqi

# 105.10. Sadə Matching

Formula kimi:

```text
score =
required_capabilities_matched
/
total_required_capabilities
```

Agent A:

```text
3 / 3 = 1.0
```

Agent C:

```text
3 / 3 = 1.0
```

İndi başqa kriteriyalar lazımdır.

---

# 105.11. Capability Matching kifayət deyil

İki agent eyni capability-yə sahib ola bilər.

Amma:

```text

busy

Agent C:
available
```

→ C seçilir.

Başqa vəziyyət:

```text
A:
cost = low

C:
cost = high
```

→ A seçilə bilər.

# 105.18. Agent Affinity

# 105.36. Supervisor ≠ Architect

Supervisor əsasən:

```text
execution orchestration
```

```text

```

edir.

---

# 105.37. Centralized vs Decentralized

Centralized:

```text
             ORCHESTRATOR
          /       |       \
       Agent    Agent    Agent
```

Üstünlük:

* control
* observability
* deterministic workflow

Çatışmazlıq:

* bottleneck
* single orchestration dependency

---

# 105.38. Decentralized

```text
Agent ↔ Agent ↔ Agent
```

Agent-lər bir-biri ilə negotiation edə bilər.

Daha flexible-dir.

Amma:

* unpredictable
* harder to debug
* harder governance

ola bilər.

---

# 105.39. SDD üçün hansı daha uyğundur?

```text

 ↓
```

# PHASE 106 — CONTEXT ENGINE & KNOWLEDGE RESOLUTION

Növbəti dərsdə daha kritik problemə keçəcəyik:

> **AI agent task-ı icra etmək üçün `.sdd`-nin hansı hissələrini oxumalıdır?**

Çünki böyük project-də:

```text
10,000 files
500 APIs
300 DB tables
100 decisions
200 skills
```

ola bilər.

AI-yə hamısını vermək həm bahalı, həm də təhlükəlidir.

Ona görə:

```text
Task
 ↓
Context Resolver
 ↓
Relevant Knowledge Graph
 ↓
Minimal Context
 ↓
Agent
```

modelini quracağıq.

Burada **context graph, dependency-aware retrieval, relevance, token budget, context priority, stale context, context versioning və "AI nəyi oxumalıdır?" problemini** SDD səviyyəsində həll edəcəyik.
