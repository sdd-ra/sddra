# PHASE 134 — `SELF-EVOLVING SDD`

Burada artıq `.sdd`-nin ən fərqləndirici xüsusiyyətlərindən birinə gəlirik:

> **AI sadəcə `.sdd`-dən istifadə etmir — işlədikcə `.sdd`-ni inkişaf etdirir.**

Amma çox vacib sərhəd:

> **AI özbaşına qaydaları dəyişməməlidir. O, dəyişiklik təklif edir → əsaslandırır → validate edir → yalnız icazə verilən səviyyədə promote edir.**

---

# 1. Əsas Evolution Loop

```text
OBSERVE
   ↓
DISCOVER
   ↓
CLASSIFY
   ↓
COMPARE
   ↓
GAP?
 ┌─┴─┐
NO  YES
│    ↓
│   PROPOSE
│    ↓
│   VALIDATE
│    ↓
│   PROMOTE
│    ↓
└── VERSION
      ↓
   RE-EVALUATE
```

Bu loop `.sdd`-nin əsas lifecycle-ına çevrilə bilər.

---

# 2. AI yeni məlumat görəndə

Məsələn AI kodu analiz edir və görür:

```text

```

```text

```

üç dəfə birlikdə istifadə olunur.

AI düşünməməlidir:

> "Yeni skill yaradıram."

Əvvəl:

```text
DISCOVERY
```

yaratmalıdır.

# 8. `PARTIAL_MATCH`

Ən maraqlı hal budur.

Mövcud:

```text
@skill.retry
```

Yeni:

```text
retry + idempotency + transaction
```

AI görür:

> Mövcud skill-in scope-u kifayət etmir.

Yeni skill:

```text
@skill.transaction-safe-retry
```

təklif edir.

Amma:

```text
BUILDS_ON
    @skill.retry
```

olur.

# 9. Skill Tree

Beləliklə skill-lər flat list olmur:

```text

├── retry
│   ├── basic

│   └── transaction-safe
```

Bu **skill inheritance** kimi işləyə bilər.

---

# 10. Amma inheritance də məcburi deyil

Daha ümumi relationship:

```text

    EXTENDS
    @skill.retry
```

və ya:

```text
BUILDS_ON
```

istifadə edilə bilər.

Çünki klassik inheritance terminini hər yerdə istifadə etmək düzgün deyil.

---

# 50. Final prinsip

`.sdd` üçün bunu ayrıca əsas prinsip kimi yazmağı tövsiyə edirəm:

> **The system must prefer discovering and extending existing engineering knowledge over creating duplicated knowledge.**

və ikinci:

> **No knowledge becomes canonical merely because an AI generated it.**

və üçüncü:

> **Every important evolution must have evidence, provenance, and a reason.**

# PHASE 135 — `SDD QUERY LANGUAGE`

Növbəti mərhələdə artıq çox maraqlı bir problem qalır:

Sistem böyüdükcə human və AI belə sorğular verməlidir:

```text
@payment
```

```text
@ddd where used=true
```

```text
show all architecture decisions affecting @payment
```

```text
why @task.T2041 uses @skill.idempotency?
```

```text
what breaks if @concept.transaction changes?
```

```text
find duplicated concepts
```

```text
find skills that have no proof
```

```text
show unknowns blocking @task.T2041
```

```text
show all architecture drift
```

Buna görə növbəti səviyyədə `.sdd` üçün **sadə, AI-friendly və Human-friendly query language** qurmaq olar.

Ən yaxşı variantda insan SQL/GraphQL öyrənmədən:

```text
@payment
@ddd
@task:open
@risk:high
@unknown:blocking
@impact:@concept.idempotency
```

kimi qısa syntax ilə bütün engineering graph-ı idarə edə biləcək.
