# SDDRA — `.sdd` Evolution Plan: PHASE 120–124 + SpecDD Integration

## Goal

Merge the five `prompts/inbox/` requirement files (165–170) and the
`bootstrap.project.md` SpecDD override into the live `.sdd/` filesystem,
progressing the system from **L2 (Defined)** toward **L3/L4**.

The inbox files describe three new system layers:

| File | Phase | Core Concern |
|------|-------|-------------|
| 165–166 | PHASE 120 — Evidence Graph & Knowledge Trust | Every knowledge entry needs evidence, trust metadata, lifecycle status, and a health report. |
| 167 | PHASE 122 — Knowledge Compression & Canonicalization | Canonical concepts, relationship vocabulary, knowledge diff/versioning. |
| 168 | PHASE 123 — AI Working Memory | 4-tier memory model, context builder, context budget, negative knowledge, consolidation. |
| 169 | PHASE 124 — AI Autonomous Execution Loop | Task state machine, loop protection, done-proof, execution trace, learning gate. |
| bootstrap.project.md | SpecDD Bootstrap | CASE specs, task markers, 5-step chain, test-discovery gate, manual QA gates, security ledger. |
| 170 | Loperasiyon (operational rules) | `.sdd` local search, architecture diagrams, pre-flight doc, code quality, L0/L1 layers. |

## Scope

- **In scope**: `.sdd/` spec files, templates, INDEX references, new `.sdd` command specs (`sdd-health` extension, `sdd-knowledge`), and integration rules that link the new phases to the existing chain graph and task lifecycle.
- **Out of scope**: Actual runtime implementation (Go compiler, agent runtime) — that is Phase 9 in `WORK-PLAN.sdd`. This plan delivers the **specifications** only.

## Key Decisions (resolved)

1. **File format**: All new `.sdd/` files follow the canonical header format
   (`Category: Name` / `Purpose:` / `Owns:` / `Rules:` / `Navigation:` /
   `State: +`) per `.sdd/PROJECT.sdd` rule R7 and `DOCUMENTATION.md` §2.
2. **Naming**: New knowledge references use `@concept.*`, `@candidate.*`,
   `@skill.*`, `@pattern.*` prefixes with dot-separated semantic namespaces
   per PHASE 122 §3.
3. **Memory is runtime-only**: Working memory and TMP memory are NOT
   persisted to `.sdd/` — they live in `.sdd/runtime/` per PHASE 123 §36.
4. **Trust hierarchy**: Explicit project constraints > decisions > validated
   project skills > established org knowledge > general best practices > AI
   suggestions (PHASE 120 §13).
5. **Loop protection**: 5 guards (max iterations, failure budget, no-progress
   detection, duplicate-action detection, state transition rules) + human
   escalation (PHASE 124 §34).

## Data Flow Summary

```
HUMAN intent → Context Builder → Knowledge Compiler → Task Context
                    ↓
               Execution Loop (PLAN → IMPLEMENT → TEST → REVIEW)
                    ↓
          ┌──────────┴────────────┐
      PASS                    FAIL (classify)
          ↓                        ↓
   Done Proof              Failure → Fix → Re-test
                           (loop guards check each iteration)
                    ↓
           Knowledge Consolidation
           (DROP | ARCHIVE | LINK | PROMOTE)
                    ↓
              LONG-TERM KNOWLEDGE
```

## Risks

| Risk | Mitigation |
|------|-----------|
| Over-engineering the knowledge graph | Start with core reference/concept schema; extend incrementally. |
| `.sdd/` immutability conflicts with dynamic trust/ledger updates | Use `.sdd/runtime/` for dynamic state; keep `.sdd/` specs immutable. |
| Circular references in knowledge graph | Add `drift.sdd` validation check per `.sdd/graph/` schema. |
| Token explosion from knowledge loading | Enforce Context Budget (PHASE 123 §10) and `always_load` allowlist. |
| Human gates blocking autonomous progress | Implement autonomy levels L0–L5 (PHASE 124 §18) with explicit policy. |

## Validation Plan

- `sdd-health` extension validates: (a) all new `.sdd` files have required
  headers, (b) `@reference` targets resolve, (c) knowledge statuses are
  well-formed, (d) flow-index trees are acyclic.
- Each phase deliverable has a `Test:` block in the task list; an
  implementation agent should run `.sdd/testing/scripts/run.ps1 -Category unit`
  after each phase.

   - `.sdd/references/` — trust-weighted references (PHASE 120 §9, §3)

### Phase 1 — PHASE 120: Evidence Graph & Knowledge Trust

3. **Create `.sdd/concepts/KNOWLEDGE-MODEL.sdd`**
   - Defines the 4-tier knowledge lifecycle: OBSERVED → CANDIDATE →
     VALIDATED → ESTABLISHED (§2).
   - Defines `trust`, `confidence`, `evidence`, `provenance` metadata
     schema (§3, §8).
   - Defines evidence types: CODE, TEST, TASK, DECISION, PROJECT,
     PRODUCTION, EXTERNAL, HUMAN (§5).

4. **Create `.sdd/knowledge/KNOWLEDGE-LIFECYCLE.sdd`**
   - The full knowledge extraction pipeline: TMP → OBSERVATIONS →
     CONCEPT EXTRACTION → SEMANTIC CLUSTERING → CANONICALIZATION →
     RELATION DETECTION → REFERENCE CREATION (§7 of PHASE 122).
   - `knowledge-promotion.sdd` sub-policy: how CANDIDATE → VALIDATED →
     ESTABLISHED.

5. **Create `.sdd/references/index.sdd`**
   - Registry of all knowledge references with `trust`, `confidence`,
     `status`, `evidence_count`, `projects`, `tasks`, `human_verified`,
     `production_verified` fields (§3, §9, §10 of PHASE 120).
   - Priority hierarchy (§13 of PHASE 120).

6. **Create `.sdd/commands/sdd-knowledge.sdd`**
   - New CLI command spec: `@sdd.health`-equivalent for knowledge.
   - Outputs knowledge health report: references count, established count,
     candidates, deprecated, conflicts, knowledge gaps, unused references,
     duplicate concepts (§20 of PHASE 120).
   - Supports `knowledge diff` against previous snapshot (§10 of PHASE 122).

7. **Migrate existing best-practices/skills to trust model**
   - Tag each existing `@skill.*`, `@architecture.*`, `@best-practice.*`
     in `.sdd/skills/` and `.sdd/concepts/` with a `trust:` and `status:`
     field.
   - Add `evidence:` cross-references where applicable.

10. **Create `.sdd/knowledge/COMPRESSION.sdd`**
    - Knowledge compression pipeline: 20 observations → semantic
      clustering → 1 concept → contextual rules (§5 of PHASE 122).
    - Knowledge diff format: `+ new`, `~ changed`, `- removed`,
      `! conflicted`, `?` unknown (§10).

11. **Create `.sdd/knowledge/VERSIONING.sdd`**
    - Knowledge versioning: v1, v2, … with `changed_reason:` field (§12
      of PHASE 122).
    - Knowledge rollback procedure: deprecated → rollback (§14).

12. **Create `.sdd/knowledge/GOLDEN-RULES.sdd`**
    - The 10 knowledge principles from PHASE 122 §28:
      1. Prefer reuse over creation
      2. Prefer linking over copying
      3. Prefer specialization over duplication
      4. Prefer evidence over assumption
      5. Prefer canonical concepts over synonyms
      6. Never silently learn
      7. Never silently overwrite
      8. Never silently delete
      9. Scope every project-specific rule
      10. Preserve why a decision was made

13. **Create `.sdd/lessons/REJECTED-APPROACHES.sdd`**
    - Negative knowledge store per PHASE 123 §18:
      `@rejected.<name>` with `reason:`, `failed_approach:`,

    - Integrates with Phase 120 knowledge diff (`! conflicted`).

### Phase 4 — PHASE 124: AI Autonomous Execution Loop

19. **Create `.sdd/tasks/TASK-STATE-MACHINE.sdd`**
    - 10-state task lifecycle (§1 of PHASE 124):
      DISCOVERING → PLANNING → IMPLEMENTING → TESTING → REVIEWING →
      FIXING → DOCUMENTING → LEARNING → COMPLETED / BLOCKED / ESCALATED.
    - Sub-state transitions: TESTING → FAILED → FIXING → TESTING (§1).

20. **Create `.sdd/tasks/LOOP-PROTECTION.sdd`**
    - 5 loop guards (§34): max iterations, failure budget, no-progress
      detection, duplicate-action detection, state transition rules.
    - 6th guard: human escalation (§14 of PHASE 124).
    - `LOOP_SCORE` calculation (§35): same_action (+30), same_error (+25),
      no_progress (+30), plan_reverted (+20), new_evidence (-20),
      meaningful_change (-30). Threshold ≥ 60 → `LOOP_RISK_HIGH`.

21. **Create `.sdd/tasks/FAILURE-CLASSIFICATION.sdd`**
    - 9 failure types (§6 of PHASE 124):
      BUILD_FAILURE, TEST_FAILURE, LOGIC_FAILURE, ARCHITECTURE_FAILURE,
      CONSTRAINT_FAILURE, ENVIRONMENT_FAILURE, KNOWLEDGE_GAP, AMBIGUITY,
      EXTERNAL_DEPENDENCY.
    - Failure → action map (§7): TEST_FAILURE → inspect test + implementation,
      KNOWLEDGE_GAP → retrieve knowledge, AMBIGUITY → human escalation, etc.

22. **Create `.sdd/tasks/EXECUTION-CONTRACT.sdd`**
    - Per-task execution contract (§20 of PHASE 124):
      goal, allowed, allowed_actions, forbidden, approval_required,
      max_iterations, max_failure_budget, autonomy level.

23. **Create `.sdd/tasks/AUTONOMY-POLICY.sdd`**
    - Autonomy levels L0–L5 (§18 of PHASE 124):
      L0 observe-only → L5 autonomous multi-task.
    - Project-level `@policy.autonomy` per domain (§19):
      payment max L2, security max L1, documentation max L4.

24. **Create `.sdd/tasks/DONE-PROOF.sdd`**
    - Done proof template (§10 of PHASE 124):
      requirements ✓, tests ✓ (unit/integration/BDD), architecture ✓,
      review ✓, documentation ✓.
    - Distinction: Functional Done vs Engineering Done (§11).

25. **Create `.sdd/tasks/PARTIAL-DONE.sdd`**
    - Partial completion model (§12 of PHASE 124):

26. **Create `.sdd/workflow/execution-loop.sdd`**
    - Full execution machine diagram (§33 of PHASE 124):

27. **Create `.sdd/workflow/learning-gate.sdd`**

## Open Questions

1. **Knowledge graph storage**: Should `.sdd/` use a physical graph
   database (PostgreSQL + graph extensions) or pure filesystem
   `@reference` links? The `bootstrap.project.md` mentions PostgreSQL
   in `.sdd/architecture/`, but current `.sdd/` is filesystem-only.
   → **Recommendation**: Keep filesystem-first; add `graph.sdd` schema
   for a future runtime compiler. Mark as TODO in
   `.sdd/architecture/data.sdd`.

2. **Dependency ledger location**: Should the dependency ledger live in
   `.sdd/runtime/` (immutable specs) or per-project `.specdd/`?
   → **Recommendation**: `.specdd/dependency-ledger.md` per project
   (runtime artifact), with `.sdd/security/DEPENDENCY-LEDGER.sdd` as
   the spec that governs its format and lifecycle.

3. **Layer gate vs. autonomy**: If autonomy is L4 for a domain, should
   the L0→L1 manual QA gate still require human hash responses?
   → **Recommendation**: Yes — manual QA is a human trust boundary, not
   an automation boundary. See PHASE 120 §13 priority hierarchy.

4. **`sdd-knowledge` health command scope**: Should it cross-reference
   `flow-index.md` and `fix-index.sdd` from each project?
   → **Recommendation**: Yes — the command should scan `.specdd/`
   artifacts per project and report cross-project knowledge health.
