# PHASE 125 — `AI CONSTITUTION & AUTHORITY MODEL`

İndi sistemin ən vacib təhlükəsizlik və idarəetmə qatlarından birinə gəlirik.

Əvvəlki mərhələlərdə AI:

```text
KNOW
→ PLAN
→ EXECUTE
→ TEST
→ REVIEW
→ LEARN
```

edə bilir.

Amma bir sual qalır:

> **AI-nin bunların hansını özbaşına etməyə haqqı var?**

Bunu prompt ilə həll etmək düzgün deyil.

Bunu `.sdd` daxilində **formal authority system** kimi modelləşdirmək lazımdır.

---

# 1. `Constitution` — dəyişməyən əsas qanunlar

`.sdd/constitution.sdd`

Burada project-in ən fundamental prinsipləri olur.

Məsələn:

```text
CONSTITUTION

C001
Never expose secrets.

C002
Never perform destructive operation without approval.

C003
Existing validated architecture has priority over generic best practice.

C004
Reuse existing knowledge before creating new knowledge.

C005
Never silently change an existing decision.

C006
Never mark a task completed without proof.

C007
Never learn unvalidated knowledge as permanent truth.

C008
Human approval is mandatory for irreversible high-risk changes.
```

Bunlar adi skill deyil.

Bunlar **AI-nin davranış sərhədidir.**

---

# 2. Constitution hierarchy

Mən authority-ni belə qurardım:

```text
L0  CONSTITUTION
        ↓
L1  ORGANIZATION / GLOBAL RULES
        ↓
L2  PROJECT RULES
        ↓
L3  ARCHITECTURE DECISIONS
        ↓
L4  DOMAIN RULES
        ↓
L5  TASK RULES
        ↓
L6  AI WORKING MEMORY
```

Aşağı səviyyə yuxarı səviyyəyə zidd ola bilməz.

# 5. Authority Matrix

AI üçün belə matrix yarada bilərik:

| Action                       | AI | Approval                |
| ---------------------------- | -- | ----------------------- |
| Read code                    | ✅  | —                       |
| Analyze code                 | ✅  | —                       |
| Add test                     | ✅  | —                       |
| Refactor internal code       | ✅  | —                       |
| Add documentation            | ✅  | —                       |
| Add skill candidate          | ✅  | —                       |
| Promote knowledge            | ⚠️ | Depending on confidence |
| Change architecture          | ⚠️ | Usually                 |
| Change public API            | ⚠️ | Yes                     |
| Delete production data       | ❌  | Human                   |
| Change security policy       | ❌  | Human                   |
| Delete architecture decision | ❌  | Human                   |

**Policy-dir.**

# 7. Risk × Authority

Məsələn:

```text
READ file
risk = 0
```

→ automatic.

```text
MODIFY internal function
risk = low
```

→ automatic.

```text
CHANGE public API
risk = high
```

→ approval.

```text
DELETE database data
risk = critical
```

→ human-only.

---

# 8. `Capability` və `Authority` fərqlidir

Bu incə, amma çox vacibdir.

AI-nin capability-si:

> bunu texniki olaraq edə bilərəm.

Authority:

> bunu etməyə icazəm varmı?

Məsələn AI:

```text
can_delete_database = true
```

ola bilər.

Amma:

```text
authority.delete_database = false
```

ola bilər.

Yəni:

> **Ability ≠ Permission**

---

# 9. Tool permissions də `.sdd`-yə bağlana bilər

Məsələn:

```text

    read: allowed
    write: allowed
    delete: restricted

database:
    read: allowed
    write: restricted
    drop: forbidden

deployment:
    staging: allowed
    production: approval
```

Bu, AI agent layer ilə `.sdd` arasında körpü yaradır.

# 13. `Human Gate`

AI approval tələb edəndə sadəcə:

> "Can I do this?"

deməməlidir.

Human-a decision package verməlidir:

```text
APPROVAL REQUEST

Action:
    Change payment transaction boundary

Why:
    Current implementation violates atomicity

Impact:
    PaymentService
    BalanceService

Alternatives:
    A — keep current architecture
    B — transactional boundary in application service
    C — distributed transaction

Recommended:
    B

Risk:
    HIGH

Rollback:
    available

Evidence:
    TASK-1023
    TEST-882
    @decision.atomic-balance
```

Human sadəcə:

```text
APPROVE
REJECT
MODIFY
```

edə bilər.

# 14. `Decision Delegation`

# 16. Authority inheritance

Project:

```text

```

Module:

```text

```

Module project-in permission-ını **azalda bilər**, amma artıra bilməz.

```text

    L3

    L1
```

mümkündür.

Amma:

```text
Project:
    L1

Security module:
    L4
```

olmaz.

# 17. `Least Authority`

Əsas prinsip:

> AI-yə lazım olduğundan artıq authority vermə.

Məsələn documentation task üçün:

```text
read source: yes

```

# 18. `Temporary Authority`

Bəzən task üçün xüsusi permission lazımdır.

Məsələn migration:

```text
temporary:
    database.write
```

Amma:

```text
scope:
    staging

expires:
    TASK-2031 completion
```

Task bitəndə permission avtomatik yox olur.

# 19. `Break Glass`

# 21. AI öz authority-sini dəyişə bilməz

Bu mütləq Constitution rule olmalıdır:

```text
C009

AI MUST NOT:
    modify its own authority
    modify approval rules
    disable audit
    modify constitution
```

```text
AI:
    "I need more permission."
    ↓
AI gives itself permission
```

kimi absurd vəziyyət yaranar.

# 28. Burada çox vacib bir konsept yaranır

> **Nə doğrudur?**

> **AI necə davranmalıdır?**

> **İndi nə etməlidir?**

# 31. Ən vacib yeni prinsip

## **AI should not navigate the filesystem to discover how to think.**

AI:

```text
folder
→ guess
→ search
→ guess
```

etməməlidir.

Əvəzində:

```text
intent
→ semantic index
→ relevant references
→ authority
→ skill chain
→ execution
```

olmalıdır.

Bu, sənin əvvəl dediyin:

> "AI hər dəfə mən deməməliyəm ki DDD istifadə et"

problemini kökündən həll edir.


Bunların hamısını bir-birinə bağlayan son dərəcə vacib bir layer qalır:

# **PHASE 126 — `AI ORCHESTRATION & SKILL GRAPH`**

Burada artıq:

```text
Task
 ↓
Skill A
 ↓
Skill B
 ↓
DDD Reference
 ↓
Architecture Reference
 ↓
Implementation Skill
 ↓
Testing Skill
 ↓
Review Skill
 ↓
Documentation Skill
 ↓
Learning Skill
```

**dinamik skill graph** kimi qurulacaq.

Ən maraqlı hissəsi isə budur:

> AI sadəcə "skill seçməyəcək". Task-ın vəziyyətinə görə **növbəti skill-i özü discover edəcək**, amma bunu `allowed transitions` və `skill contracts` daxilində edəcək.

Beləliklə `.sdd` artıq statik folder collection yox, **özünü idarə edən engineering workflow graph** formasına keçəcək.
